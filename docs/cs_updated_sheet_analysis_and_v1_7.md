## 精査サマリ

CSが作ったのは**3種類の異なるもの**で、行き先が違う。

| CSのタブ | 中身 | 行き先 |
|---|---|---|
| `AI_*` 知識5本（53KB） | 章立ての構造化ルール文書 | **kb_rules に取り込む**（同梱データ） |
| `Core_System_Prompt` ＋ `AI_System_Prompt_*` 4本 | AIの振る舞い指示 | **プロンプトにマージ**（kb_rulesには入れない※CSも明記） |
| `Questions to Set` | 14トピックのメニュー案 | **menu_categories.json の見直し材料** |
| 既存19タブ | 16本は無変更、3本のみ差分 | 該当ルールのみ更新 |

**「全面刷新」ではなく「新規タブ5本の追加」が本体。** 既存タブは
`Replacement_Plan change Product`(83行入替) / `REPLACEMENT AND CHANGE PLAN RUL`(13行) /
`eSIM RM Call Plan`(数行) 以外は完全に無変更。

### 内容の質は高く、我々のv1.6と思想が一致している
CSは独立に同じ結論に到達している:「一般論で答えず1つ質問して絞り込め」「一度に1問だけ」
「アカウント依存の事実は断定せず support team が確認と伝えろ」「文書にない数字を発明するな」。

### 最大の収穫: 契約グループの概念（現行ナレッジに欠落）
**2024年12月11日** を境に適用ルールが根本的に異なる。これを知らないAIは確実に誤答する。

| | PREVIOUS（2024/12/11より前） | CURRENT（2024/12/11以降） |
|---|---|---|
| 適用 | Section 18（3・6は適用外） | Section 3・6（18は適用外） |
| SIMデポジット額 | **金額を絶対に言わない**（文書に記載なし） | **¥800** |

| 未払いへの充当 | 可能 | **不可** |

## Claude Code 指示書（v1.7）

仕様書を `docs/build_spec_v1_7.md` として更新の上、Phase順に実施。各Phase前にplan mode。

同梱データ: `data/kb_cs_ai_docs_import.json`（Cシリーズ105件）

### Phase 1 — 知識の取り込み（Cシリーズ105件）

- `data/kb_cs_ai_docs_import.json` を投入。CSの章立てを保持するため**1セクション=1ルール**の粒度
  （平均493文字）。従来の1行1ルールより長いが、文脈が壊れないためこの形とする
- 新フィールド `topic_hint`（cancel/return/refund/replace/internet）を持たせてあるので、
  `menu_categories.json` の該当トピックのスコープに含めること
- `needs_review=true` の2件は pending_review
- **重複対策**: 既存ナレッジ（R/P/Fシリーズ）に同じ内容の古いルールが存在する可能性が高い。
  特に解約・返却・デポジット関連。Cシリーズと矛盾する既存ルールを検出してリスト報告し、
  承認を得てから `status='disabled'` にすること。**Cシリーズを正とする**

### Phase 2 — 契約グループの実装（今回の中核）

現行システムに完全に欠落している概念。誤答の温床なので優先度が高い。

- 解約・デポジット関連のトピック別プロンプトに以下を組み込む:
  - **契約開始日を確認するまで、Section 3/6 と Section 18 のどちらを適用するか決めない**
  - PREVIOUS契約のSIMデポジット額は**絶対に金額を述べない**（文書に記載がないため）
  - CURRENT契約のみ ¥800、かつ「次回請求からの割引」（銀行振込ではない）
  - 契約開始日は顧客の自己申告であり未確認扱い（最終確認は support team）
- 実装後、テストケースを追加: PREVIOUS契約でデポジット額を聞かれても金額を言わないこと

### Phase 3 — プロンプトのマージ（置き換えではない）

**CSのプロンプトで全面置換しないこと。** 我々のv1.6には、CSが知らない制約
（金額ポリシー、社内用語禁止、多言語、JSON出力形式、カテゴリスコープ、PIIマスキング）が
組み込まれており、置換するとこれらの安全装置が消える。

我々の骨格を維持したまま、CSのCore_System_Promptから以下を**取り込む**:

1. 「一般論や『場合による』で答えるな。1つ質問すれば実際の答えが出せるなら、必ず質問しろ」
   （我々の診断フローより踏み込んだ表現。そのまま採用）
2. 「一度に1問だけ。複数質問のチェックリストを送るな（フォームのようで、どうせ最初しか答えない）」
3. 「顧客が既に話した情報は聞き直すな。持っている情報を認めた上で、足りないものだけ聞け」
4. **「日付や数値の純粋な計算は直接やってよい（エスカレ不要）。ただしアカウント記録に依存する
   事実は断定するな」** — 我々に無い有用な区別。採用する
5. 「顧客の主張だけを根拠に、手数料の免除・返金の承認・未払いの有無・金額の正しさを断定するな」
6. エスカレ時は「これまでの会話の要約」を添える（顧客が繰り返さずに済む）
7. トーン: 「会話的・温かく・簡潔。フォームのようにしない。尋問されている感じを与えない
   （必要なら『どのルールが当てはまるか確認するため』と理由を添える）」

**トピック別の情報収集順序**も採用する（例: 解約 = 契約グループ → サービス種別 → 利用期間 →
Re-issue状態 → 希望解約日と申請日 → Wi-Fiなら返却状況）。
これは Phase 3（v1.6のエスカレ前情報収集）の項目定義として使える。

### Phase 4 — トピックメニューの見直し

CSは14項目のメニューを提案（`Questions to Set`）。現行10タイルとの主な差分:

| CS案にあり現行になし | 判断 |
|---|---|
| Deposit refund inquiry を Refund から独立 | **採用推奨**（デポジットは問い合わせが多く、契約グループ判定が必要な特殊トピック） |
| Holiday plan / Call plan / Data plan / Plan issue | **不採用推奨**。現行の Plans & prices に集約。4つに割ると顧客が迷う |
| Signal Problem / APN settings / Internet Not working を3分割 | **不採用推奨**。顧客には区別がつかない。現行どおり1タイルにまとめ、Phase 2の診断フロー（聞き返し）で切り分ける方が確実 |
| Replace a lost or broken SIM/device（紛失と故障を統合） | **検討**。現行は Lost と Replacement が別タイル。CS案の方が顧客視点に近い可能性 |

→ 上記の判断でCS案を取り込み、**最終的に11タイル**（現行10＋Deposit refund）を推奨。
実装前にこの構成でよいか確認すること。

### Phase 5 — 既存タブの差分反映

- `Replacement_Plan change Product`(83行入替) / `REPLACEMENT AND CHANGE PLAN RUL`(13行) /
  `eSIM RM Call Plan - Unlimited I`(数行) の3タブのみ差分あり
- 該当する既存ルール（P/Rシリーズ）を特定し、新しい内容に更新。差分をリスト報告してから適用

### 完了条件

- 受け入れ基準に追加:
  - PREVIOUS契約の顧客にデポジット金額を述べない
  - CURRENT契約では ¥800・次回請求からの割引と正しく答える
  - 契約開始日を確認せずに解約ルールを断定しない
  - 「一度に1問だけ」が守られている（複数質問を並べない）
  - 日付計算（例: 通知期間が足りているか）は自分で計算して答える
- 本番デプロイまで実施
