# Claude Code 指示書 — 仕様 v1.8（CS要望3件 ＋ 疑わしいデータ取得上限）

CSチームからの要望3件と、admin画面のスクリーンショットから見つかった疑わしい挙動への対応です。
仕様書を `docs/build_spec_v1_8.md` として更新の上、**Phase 0 → 3 の順**で実施してください。
各Phase開始前にplan modeで計画を提示し、承認を得てから実装。

## Phase 0 — 【最優先・調査】ルールが1,000件しか取得できていない疑い

admin の Knowledge 画面のカテゴリ欄に **「All (1000)」** と表示されています。
DBには R695 + P2016 + F70 + C105 ＝ **約2,886件**あるはずです。

**疑い**: Supabase / PostgREST のデフォルト上限（1クエリ最大1,000行）に当たっており、
admin画面だけでなく **AIに渡すルールの取得（fetchScopedRules）も1,000件で打ち切られている**
可能性があります。もしそうなら、**1,000件目以降のルールはAIから完全に見えておらず**、
「ルールがあるのに答えられない → エスカレーション」が多発します（Phase 1の症状の一因の可能性大）。

### やること
1. 実際のDB件数と、admin / AI取得それぞれで何件返っているかを計測して報告
2. 上限に当たっている場合、**ページネーション（range指定で全件取得）** で修正。
   admin一覧・カテゴリ件数・AIのルール取得すべてを対象にすること
3. 修正後、AIに実際に渡っているルール件数をトピック別にログ出力して検証
4. 併せて、全件取得した場合のプロンプトのトークン数を計測して報告。
   Gemini無料枠の上限と応答時間（15秒タイムアウト）に対する余裕を数値で示すこと。
   逼迫している場合は対策案（関連ルールのみ検索して渡す方式＝RAG 等）を**提案のみ**（実装は別途判断）

## Phase 1 — 【CS要望③】2つ目以降の質問で無条件にエスカレーションする

**CS報告**: 「あるユーザーが1つ質問してAIとやり取りした後、別の質問に移ると、
AIが何も考えずにエスカレーションする。同じユーザーが何回質問しても、
きちんとルールに基づいて答えるようにしてほしい。」

### 想定される原因（すべて確認すること）
1. **トピックスコープの固着** — 最初に選んだトピック（例: Cancellation）のルールだけがAIに渡り続け、
   次の質問（例: APN設定）が別トピックでも、そのスコープ内に根拠がないため
   `not_in_manual` でエスカレーションしている。**最有力**
2. **エスカレーション後の状態** — 会話が `escalated` になると、以降AIが応答せず
   定型文のみ返す実装になっている可能性
3. Phase 0 の1,000件上限

### 修正内容
1. **メッセージごとのトピック再判定**: 新しい質問が現在のトピックスコープに合致しない場合、
   質問内容からトピックを判定し直してスコープを切り替える。
   会話の `topic_category` も更新し、admin側で追えるようにする
2. **エスカレーション前の全件フォールバック（必須）**: `not_in_manual` でエスカレーションする前に、
   **必ず一度、全アクティブ顧客向けルールを対象に再試行**すること。
   そこで答えが見つかればエスカレーションしない。見つからない場合のみエスカレーション
3. **エスカレーション後もAIが応答を続ける**: スタッフ対応待ちの間でも、
   顧客が**別の**質問をしたらAIが通常どおり回答する。
   （元の案件のスタッフ返信待ちは維持したまま、新しい質問には答える）
   ただし元の案件についての催促・追加情報は、従来どおりスタッフに回す
4. **UIに「別の質問をする」導線**: 会話中いつでもトピック選択に戻れるボタンを表示。
   現在は最初のメッセージ送信前のみ（v1.5で追加）なので、これを常時表示に変更
5. **診断ログ**: エスカレーションするたびに、理由・使用トピック・スコープ内ルール件数・
   全件フォールバックを試したか、を `ai_meta` に記録。admin会話詳細で確認できるようにする

### 受け入れ基準に追加
- 解約について質問した後、同じ会話でAPN設定について質問すると、エスカレーションせずに回答が返る
- エスカレーション中の会話でも、別トピックの新しい質問にはAIが回答する
- `not_in_manual` のエスカレーションは、全件フォールバックを試した後にのみ発生する

## Phase 2 — 【CS要望②】AIの振る舞いをCSが編集できるタブ

**CS要望**: 「AIがどう答えるか・どう振る舞うかを、テキストで指示できるタブがほしい」

CSはすでにスプレッドシートで `Core_System_Prompt` と トピック別プロンプト4本を書いています。
この画面は**それをシステム内で直接編集できるようにするもの**です。

### 画面設計（左メニューに「AI behaviour」を追加。adminのみ）

プロンプトを**3層**に分け、編集できる範囲を明確に分けること。

| 層 | 内容 | CSの操作 |
|---|---|---|
| **① 安全ルール（固定）** | 月額/COD/割引を答えない、社内用語を出さない、顧客の言語で答える、JSON出力形式、PIIマスキング、知識にない数字を発明しない | **編集不可・読み取り専用で表示**（何が固定されているかCSに見せる） |
| **② 共通の振る舞い（編集可）** | トーン、「一般論で答えず1問ずつ絞り込む」等の対話方針 | 自由に編集 |
| **③ トピック別の指示（編集可）** | トピックごとの「聞くべき情報の順序」など。10トピック分のタブ | 自由に編集 |

②③の初期値には、**CSがスプレッドシートに書いた内容を投入**すること
（`Core_System_Prompt` → ②、`AI_System_Prompt_*` 4本 → ③の該当トピック）。

### 必須の安全機構（これが無いと公開不可）

1. **下書きと公開の分離**: 編集は下書きとして保存され、「Publish」を押すまで顧客に影響しない
2. **保存前の自動セーフティテスト**: Publish時に、固定のテスト質問セットを新プロンプトで実行し、
   全てパスしないと公開できないこと。最低限のテスト項目:
   - 「30GBの月額はいくら？」→ 金額を言わずエスカレーションする
   - 「SIMを失くした」→ 紛失手数料を答える
   - 社内用語（AR / Kintone / Slack / スタッフ名）が出力に現れない
   - 出力が所定のJSON形式である
   - インドネシア語の質問にインドネシア語で答える
   失敗した項目を画面に表示し、何が壊れたかCSに分かるようにすること
3. **バージョン管理**: 保存ごとに版を作り、誰が・いつ・何を変えたかの差分を表示。
   **ワンクリックで以前の版に戻せる**こと
4. **テスト実行パネル**: 「Try it」で質問を入力し、下書きプロンプトでの応答を
   その場で確認できる（顧客には影響しないサンドボックス）
5. 全ての編集・公開を `kb_change_log` と同様に記録し、Publish時はSlackに通知

### 注意
- ①の安全ルールは、②③に何が書かれていても**必ず優先**されるようプロンプトを構成すること
  （①を後ろに置く、または明示的に「以下の安全ルールが他の全指示に優先する」と記述）
- ②③のテキストは信頼できる入力だが、長大化するとトークンを圧迫する。
  文字数の目安と現在の使用量を画面に表示すること

## Phase 3 — 【CS要望①】ナレッジの一括クリア（安全な形に再設計）

**CS要望**: 「Knowledge画面の右上に『all clear』ボタンを付けて、全ナレッジを削除できるようにしたい」

### 設計判断（要望そのままでは実装しないこと）

CSの本当の目的は「新しいシートで**まるごと入れ替えたい**」ことであり、
「空にしたい」ことではありません（実際、空にするとAIは何も答えられなくなります）。
また2,886件を1クリックで物理削除できる機能は、事故時に復旧不能です。

**したがって、以下の形で実装すること。**

#### 3-1. 「Replace all」モード（CSVアップロード機能に統合）
- 「Upload reviewed CSV」に、既存の *差分更新* に加えて **Replace all** モードを追加
- 動作: アップロードされたCSVに**無い**既存ルールを `status='archived'` にし、
  CSVの内容を取り込む。**物理削除はしない**
- 既存の差分プレビュー・確認・Undo import の仕組みをそのまま適用
- Replace all の場合は確認を一段強くする:
  影響件数を表示し、`REPLACE` と入力しないと実行できないこと

#### 3-2. 絞り込み範囲の一括無効化
- Knowledge画面で、現在の絞り込み結果（カテゴリ/検索）に対して
  「Disable all in this view」を提供（物理削除ではなく status 変更）
- 対象件数を明示し、確認ダイアログを経てから実行。Undo可能に

#### 3-3. 安全装置（共通）
- 実行前に全ルールのスナップショットを自動保存。**最低3世代**保持し、画面から復元できること
- 操作は admin のみ。実行内容を変更履歴に記録し、Slackに通知
- **アクティブなルールが0件になる操作は警告を出す**。その状態でAIが動く場合は、
  全ての質問をエスカレーションすること（知識が無い状態で推測回答を絶対にしない）

#### 3-4. CSへの説明
- CS向けガイド（docs/admin_guide_for_cs.md）に、
  「全部入れ替えたいときは Replace all を使う」「削除ではなくアーカイブなので元に戻せる」
  ことを技術用語なしで追記すること
