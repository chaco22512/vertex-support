## Phase 1 — バグ修正（最優先・CSが実機で再現を確認）

### 1-1. 会話が途中で終了する
**症状（CS報告）**: 「still not connecting」など追い質問をしても、追加の切り分けが出ずに
「Thank you. Our support staff will reply to you within 24 hours.」で会話が終わってしまう。
別の質問を試しても同じ。**複数トピックで再現**。

- 原因を調査すること。現在プロンプトに渡す会話履歴が直近20メッセージ上限である点、
  トークン超過時の挙動、エスカレ後にAIが応答を止める条件、の3点を必ず確認する
- 対策として (a) 履歴上限の引き上げ、(b) 古い履歴の要約による圧縮、(c) 超過時の安全な挙動、
  を検討し実装。**無言で会話が終了する経路を残さないこと**（仕様5.4違反）
- 調査結果と採用した対策を報告すること

### 1-2. 「Something else」ボタンが即エスカレになることがある
**症状（CS報告）**: Something else を押しても自由入力が開かず、エスカレ文言が出る場合がある。
- 再現条件を特定して修正。自由入力が必ず開くこと（受け入れ基準22）

### 1-3. 🚨 公開ブロッカー: 未記入プレースホルダ
CS提供の Plans FAQ に `[insert cheapest plan name/price]` が未記入のまま含まれている。
- 同梱データでは該当ルールを `ai_can_answer=false` としてある。**この状態を維持**すること
- 加えて、**ナレッジ全体に対して未記入プレースホルダ検出のバリデーション**を追加する
  （`[insert`, `[TBD`, `[TODO`, `xxx` 等のパターンを含むルールは
  インポート時に自動で pending_review にし、警告を出す）

## Phase 2 — 診断フロー（今回の中核・AIに「聞き返す」選択肢を追加）

**CSの指摘**: 「no signal」「pocket wifiが繋がらない」は原因が複数（APN設定・データ残量・
端末設定・支払い停止・電波状況…）あるのに、AIが状況を確認せず一つの解決策を即答している。
意図の把握は合っていても、実際の状況が違えば誤誘導になる。

CSが提示した理想フロー: 意図特定 → 種別分類 → **情報収集** → 解決策 → 解決確認 → 必要時エスカレ

### 2-1. AI出力に "ask" を追加
```json
{
  "action": "answer" | "ask" | "escalate",
  "answer": "顧客向け本文（顧客の言語）",
  "follow_up": { "question": "...", "options": ["...", "...", "..."] },  // action="ask" のとき必須
  "reason": "...", "rule_ids": [...], "detected_language": "..."
}
```
既存の `escalate` boolean は `action` に統合してよい（後方互換不要）。

### 2-2. システムプロンプトに診断ルールを追加
- 原因が複数考えられる問題（インターネット不通・信号停止・ポケットWiFi不調・SIM認識不良など）は、
  即座に解決策を出さず、まず状況を特定する質問を **1つだけ** 返す（action="ask"）
- 質問には顧客が選べる **3〜5個の選択肢** を付ける
  （例: 「まったく繋がらない／遅い／Wi-Fiでのみ繋がる／SIM・端末を変えてから繋がらない／その他」）
- 十分に特定できたら解決策を返す（action="answer"）
- **単純な情報提供**（APN設定手順、支払期日、返却先住所など）は従来どおり即答してよい
- 解決策提示後は解決確認を促す

### 2-3. チャットUI
- `action="ask"` のとき、AI吹き出しの下に選択肢チップを表示。タップで送信（自由入力も併用可）
- 解決策提示後は既存の Solved / Still need help を「解決確認」として流用

### 2-4. 説明の平易化（CS指摘）
システムプロンプトに追加: 「手順は40代以上の非技術系の顧客にも分かる平易な言葉で書く。
1ステップ1文。専門用語には短い説明を添える。」

## Phase 3 — エスカレーション前の情報収集

**CSの指摘**: 内部確認が必要な案件は、引き継ぐ前にAIが必要情報を集めておくべき。
解約では SmartPit / GMO / 顧客番号 を先に取るよう明示要望あり。

- `action="escalate"` 時、連絡先入力カードの前に「状況確認カード」を挟む
- トピックに応じた項目を尋ねる（すべて**任意入力・スキップ可**。離脱防止のため必須にしない）
  - 共通: 顧客番号 または SmartPit番号 / 登録電話番号
  - トラブル系: SIM番号(ICCID) / 端末機種 / すでに試したこと
  - 解約・支払い系: SmartPit / GMO / 顧客番号
- 収集内容は conversations に保存し、**admin会話詳細の上部**と**Slack通知**に含める
  （CSRが開いた瞬間に状況が分かる状態にする）

## Phase 5 — ポリシー調整と削除

### 5-1. 手数料付記の条件分岐（Hard rule の更新）
**CSの要望**: 「Final amount will be confirmed by our staff.」を支払い・信号停止の回答から
削除したい（金額は冊子に記載済みで、かえって混乱する）。

**採用する方針（全廃はしない）**:
- **規約で固定され冊子にも記載のある金額**（延滞金¥200/¥300、再発行¥4,000、解約金¥5,000等）
  → 付記**不要**
- **顧客ごとに変動する金額**（未払い残高、最終請求額、割引適用後の金額）
  → 付記**必須**（従来どおり）

実装: `kb_rules` に `fee_is_fixed`(boolean) を追加。プロンプトで出し分ける。
既存の手数料つきルールは、規約由来の固定額を `true` に一括設定した上で、
判断が難しいものは pending_review に回して人が確認できるようにすること。

### 5-2. 価格回答の段階解禁（Plans & prices）
CSが価格入りの顧客向けFAQを作成したため、方針を部分的に変更する。

- **解禁可**（Review queueで承認後）: 通話料単価（¥33 / ¥22 per 30秒）、SMS料金表、
  ネットワーク（Rakuten/Docomo）、5G・eSIM対応、SIMロック要件、プラン仕様（データ量・通話可否等）
- **引き続き回答禁止**: 月額プラン料金、Unlimited料金、COD価格、割引額
  → CS作成のFAQ自身も「サイトかスタッフへ」としており方針は一致

同梱データではPlans関連21件すべてに `needs_review` を付与済み。上記の線引きに沿って
Review queueで個別承認する運用とする。**プロンプトの「月額価格を答えない」指示は維持すること。**

### 5-3. Pension & tax refund タイルの削除
CS判断により不要（`✕ メニューから削除必要`）。
- `menu_categories.json` から `nenkin` を削除。関連ルールはDBに残し、Others経由でのみ参照可
- locales・Rulebook Ch.1・training-deck-outline のトピック一覧を10トピックに戻す

### 5-4. CS提供待ち素材の管理
`docs/pending-cs-assets.md` を作成し、以下を「CS提供待ち」として記録:
1. **SIM Point版YouTubeチャンネルのリンク**（現行はVDMチャンネルを指す。リブランド漏れ・顧客に見える）
2. ポスター画像URL（動画の代替。通信が弱い顧客向け ※CS要望）
3. ポケットWiFi各機種の写真（紛失時の機種特定フロー用）
4. 無料交換条件の表（画像提供のため文字起こしが必要）
5. 最安プランの名称と価格（Phase 1-3 のブロッカー解消）
